1. Scope and approach

The engine (lib/flow/*), the booking rules, the readers, the document pipeline, the outbox, the console and the 237 tests are channel-independent: they consume inputs of the kinds command, callback, text, contact, caption and document, and produce messages carrying text plus inline keyboard rows. Telegram is one transport (api/telegram.js) that turns Telegram updates into those inputs and those messages into Telegram calls. WhatsApp is a second transport doing the same for Meta's Cloud API. Both run at once; every booking, document and ticket already records its channel.

Nothing in the engine changes. The work is one webhook, one API client, one keyboard adapter, template sending in the outbox drain, one small migration, and the transport's tests.

Direct vs Business Solution Provider

The Cloud API is used directly (no fee beyond per-message prices) or through a BSP — Twilio, 360dialog, Infobip — that fronts the same API with its own SDK and billing (about $0.005 per message, or ~€49–100 per number per month). The transport below targets the Cloud API; a BSP changes only the base URL, authentication and the inbound payload envelope. Recommendation: direct.

3. Cloud API behaviour that shapes the transport

BehaviourConsequence for the design
Webhook delivery and retriesMeta POSTs to the webhook and retries (with backoff, for hours) when it does not get a 2xx quickly. Same shape as Telegram: claim the message id, answer 200 at once, do the slow part in the background. processed_updates and waitUntil apply unchanged.
SignatureEvery POST carries X-Hub-Signature-256 = HMAC-SHA256(raw body, app secret). Verified on the raw body before parsing. The GET verification handshake echoes hub.challenge when hub.verify_token matches.
Message kinds inboundtext, interactive (button_reply / list_reply with the id we set), document, image, contacts, location, reaction, plus statuses (sent/delivered/read) for our outbound messages. Statuses and reactions are acknowledged and ignored; delivered/read could later feed the outbox's delivery state.
Interactive limitsReply buttons: max 3 per message, title ≤ 20 characters, id ≤ 256 bytes. List: one button opening ≤ 10 rows in sections, row title ≤ 24 characters. No inline URL buttons except CTA-URL messages. Sent messages cannot be edited or have buttons removed.
MediaInbound media arrives as an id; fetch its URL with the token, then download (URL is short-lived; media retained ~30 days). Documents ≤ 100 MB, images ≤ 5 MB. Outbound: upload to get a media id, or send by URL. Captions on inbound media are delivered with the message.
No albumsSeveral files sent at once arrive as separate messages within a second, with no group id. The batch logic (record first, read in parallel, last to finish speaks, claimed reply) works as is; the album grace wait becomes a short fixed wait on every document.
24-hour customer service windowFree-form messages only within 24 h of the client's last message; outside it, only approved templates (section 6). Template messages are billed per message by category and recipient country; utility templates inside the window are free.
IdentityThe sender is identified by wa_id (the phone number in E.164 without the plus) and a profile name. No username, no chat id distinct from the number.
Typing indicator and read receiptsSupported via the messages endpoint (mark as read, typing indicator) — used in place of Telegram's sendChatAction.
No pinning, no commandsThe pinned status card has no equivalent; slash commands are plain text.

5. Mapping the engine's messages to WhatsApp

Handlers return messages as { text, inline?: rows, keyboard?, oneTime? }. An adapter in the transport renders them:

Engine messageWhatsApp rendering
Text, no buttonssendText. Bilingual bodies are fine; WhatsApp renders Arabic right-to-left per line.
Inline rows with ≤ 3 buttonssendButtons. Titles are the label with the emoji, truncated to 20 characters; because the label carries both languages, the adapter uses a short per-language title table keyed by callback payload (e.g. menu:book → "📦 احجز / Book").
Inline rows with 4–10 buttons (edit menu, document classify)sendList with row titles from the same table; the list button reads "اختار / Choose".
More than 10 (does not occur today)Split across two list messages.
Reply keyboard "Share my number"Not sent. askNextBasic for the phone step on WhatsApp offers [Use +20…] [Another number] buttons; "Another number" → the client types it.
Documents (the PDF copy)sendDocument, caption as today.
Direct line after hoursThe text, plus sendContact so it is one tap to call.
TypingmarkRead + typing indicator on the inbound message id, in place of sendTyping.
clearButtonsNo-op; the engine already refuses stale taps with a clear message.

Truncation is asserted at build time the way cb() asserts Telegram's 64-byte payload limit today: a title over 20 characters throws in development rather than being silently rejected in production.

6. The 24-hour window and templates in the outbox

  • conversation_sessions gains last_client_message_at, stamped on every inbound message. windowOpen(session) = now − last_client_message_at < whatsapp_window_hours (setting, default 24).
  • The outbox drain, for a row with channel = 'whatsapp': inside the window → render as today and send text/document; outside → look up the template for event_type in bot_settings.whatsapp_templates and sendTemplate with the payload's fields as components. The PDF events use a template with a document header.
  • Template set (utility, ar and en): booking_confirmed (document header: the confirmation PDF; body: reference, shipment id), missing_information_requested (reference, what), booking_rejected (reference, reason), mrn_issued (mrn, reference), shipment_update (shipment, text), operations_message (reference, text). Each with one quick-reply button "Reply / رد" so the client's tap reopens the window.
  • Language choice per client: the language of their last message (Arabic script → ar), stored on the client record; falls back to en.
  • Failures Meta reports through statuses[].errors (e.g. 131047 re-engagement, 131026 not a WhatsApp user) map to the outbox's permanent-failure list, as Telegram's "bot was blocked" does today.

7. Identity, sessions and the data model

  • Session key whatsapp:<wa_id>; ctx = { channel: 'whatsapp', chatId: wa_id, clientId, userName: profile.name }.
  • Migration: clients.whatsapp_id text unique; conversation_sessions.last_client_message_at timestamptz; bot_settings rows whatsapp_templates, whatsapp_window_hours. Bookings, documents, tickets and tasks already carry channel and chat_id.
  • upsertWhatsAppClient({ waId, profileName }) mirrors upsertTelegramClient; phoneOnFile() returns the WhatsApp number first, so step 1 offers it and "Talk to an agent" never asks.
  • A person who uses both channels is two client rows unless linked by number; phoneOnFile() already matches by phone, so a Telegram client who gave the same number is recognised.
  • The pinned card (lib/pinned.js) stays Telegram-only; on WhatsApp the same events send a status text inside the window or the shipment_update template outside it.

10. Privacy and data handling

  • Stored by MKY (Supabase, AWS eu-central-1): client name and number, vehicle and route, documents and what was read from them, the conversation transcript used for question answering, tickets, the audit trail. Row Level Security on; server-only key.
  • Meta: messages and media in transit and for a limited retention; message metadata (delivery, read). Meta's WhatsApp Business terms and data processing terms apply; Meta does not receive the derived booking data.
  • OpenAI: document text/images and message text, under API data-usage terms (no training on API data); outputs validated by code before storage.
  • Privacy policy page (required by Meta): what is collected; purpose (booking and shipment handling); storage location and retention; sub-processors (Meta, Supabase, Vercel or the chosen host, OpenAI, Resend); how to request deletion. Deletion = client row, bookings, documents (storage objects), tickets, sessions, transcript.
  • Retention: a setting per table (e.g. transcripts 90 days after the last message; documents 12 months after delivery) applied by a scheduled job — a decision for MKY.
  • Egypt PDPL (Law 151/2020): EU storage, a policy, a deletion path and purpose limitation cover the practical duties; controller registration should be confirmed by MKY's counsel.
