1. Overview and architecture

The assistant is a Telegram bot (with the same engine behind a website chat widget) for a freight forwarder importing used commercial vehicles into Egypt. It takes booking requests in three steps, collects and reads the customs papers, tracks shipments from the company's own data, and routes anything else to a person. One rule governs the design:

The model may read; it may not decide. A language model reads a chassis number out of a sentence, reads a scanned invoice, and answers questions from the knowledge base. Whether a vehicle may be booked, what is missing, whether a request goes to Operations, and what the client is told are decided by code from rows in Postgres — and are tested without any model in the loop.
Telegram ──► api/telegram.js ──► lib/flow/machine.js ──► lib/flow/{booking,tracking,contact}.js
   (webhook)     │                     │                          │
                 │                     │ handled: false           ├──► lib/bookings.js    ─┐
Website ──► api/chat.js               ▼                          ├──► lib/documents.js    ├─► Supabase Postgres
                              lib/agent.js  (the model)         ├──► lib/mrn.js          │   + Storage
                                       │                          └──► lib/operations.js  ─┘
                                       └──► track_shipment · search_knowledge
                                            list_my_bookings · create_support_ticket

Outbound: Telegram Bot API · Resend (email) · staff Telegram group · Pumble webhook (optional)

A message meets the deterministic state machine first. The machine handles commands, tapped buttons, files, shared contacts, and text that answers a question it asked. Anything else — a free question — it declines, and the model answers from the knowledge base without touching the flow's state.

4. Deployment: GitHub → Vercel

  1. Changes are committed on main and pushed to origin (GitHub, shanto173/MKC-GLOBAL).
  2. Vercel's Git integration builds the web/ project and deploys it to production. A build takes about a minute.
  3. GET /api/health reports the deployed commit, the configured services, and whether every table and function the flow needs exists — the way to confirm a deploy landed.
  4. Database changes ship as files in supabase/migrations/ and are applied separately with npm run db:push (Supabase CLI, linked to the project) or by pasting the SQL into the Supabase SQL editor. Migrations are written to be safe to re-run.
  5. If code that needs a new table reaches production before its migration, lib/flow/ready.js detects the missing table and the previous engine answers instead of every message failing. The moment the migration is applied, the flow switches on with no redeploy.
  6. The Telegram webhook is registered once per deployment URL: npm run setup:webhook -- https://mkc-global.vercel.app (or /api/admin/setup). It subscribes to callback_query, without which inline buttons are dead.
Environment variables live in Vercel → Project → Settings → Environment Variables and take effect on the next deployment. Business values that must change without a deployment live in the bot_settings table (section 5) and are picked up within a minute.

7. The conversation engine

lib/flow/machine.js is the one place a transition is chosen, always from (current state, event). Handlers return { messages, patch } and send nothing themselves; the machine applies the patch to the session and hands the messages to the transport. That is what makes the whole conversation testable without Telegram.

7.1 Order of dispatch

  1. Commands from any state: /start, /menu, /book, /track, /cancel, /help, /reset.
  2. Tapped buttons (callback payloads such as bk:confirm, ct:urgent:yes). A payload says which button; the machine decides whether that is a legal move from the actual state — stale cards are refused.
  3. A shared phone number: the answer to step 1 when that was asked; kept and the open question re-asked during a booking; otherwise the number for a ticket.
  4. A caption (details written on a file), read before the file itself.
  5. A file: attached to the draft in progress, else to the request already with the desk.
  6. Text: an answer if a question is open (AWAITING_TEXT states); a numbered choice standing in for a button; a phrase that starts a flow; otherwise a question for the model.

Session state lives in conversation_sessions, never in memory: two serverless invocations a second apart are different processes. A state written by an older deployment that the code no longer knows falls back to the menu. A turn that says nothing and changes nothing writes nothing back.

7.3 Both channels

Telegram draws inline keyboards. The website widget receives the same choices as options and draws its own buttons; either way a client may type the number of a choice, except while a question is open, when a number is the answer to it.

8.1 Step 1 — who is booking

  • Order of the basics (BASIC_REQUIRED in lib/bookings.js): customer_name, customer_contact, vin, make, origin_port, destination_port. missingBasics() drives which question is next; the contact counts only when it is a dialable number, never the chat's own routing address.
  • Phone numbers are normalised to one shape by lib/phone.js: Arabic-Indic digits converted, spaces and punctuation removed, 00 → +, 8–15 digits. A shared Telegram contact gets its + restored.
  • The number is stored on the booking (customer_contact) and on the client (clients.phone), so the next booking offers it back and the next ticket does not ask.
  • A message carrying both name and number ("Ariful and my number is +49 …") is read for both: the contact is removed along with the words around it, and what remains, if it fits the question, is the answer.

8.2 Step 2 — the vehicle

  • lookupVehicle() queries vehicles, live bookings and shipments by vin_norm and returns new, known_not_booked or already_booked. The check runs wherever a chassis appears — the chassis question, a pasted block at the name step, a sentence at the make step, a caption on a file — through one function, settleVin(). A chassis is never written down unchecked.
  • Duplicate prevention is enforced three times: the flow refuses; submit_booking_request() re-checks inside the transaction; the partial unique index bookings_live_vin_unique makes it impossible at the database level.
  • The destination must match one of the five Egyptian ports (aliases in Arabic and English; "Damietta port" is not Port Said). Makes are canonicalised and split from models; Arabic makes and cities are transliterated for the paperwork; a client's company name is left as written.

8.3 Reading what people actually type

Two readers, in order. lib/flow/paste.js and lib/flow/understand.js hold fixed patterns: labelled rows and pasted tables in any copy shape (colons, pipes, backticks, row numbers glued on), a chassis anywhere in a sentence, "from X to Y", a make and model mid-sentence, "client …", phone numbers and emails, questions, refusals, requests to be elsewhere. Only when the patterns leave something missing and the message is long enough to be saying more does lib/flow/nlu.js ask the model to extract candidate fields — and every candidate goes through the same validation as a typed value. A wrong model answer costs at most one clarifying question, never a wrong port on a declaration.

8.4 Drafts

  • One draft per chat. A Book tap with a meaningful draft open offers Continue / Start over; a blank draft is reused silently; a draft untouched for draft_expiry_hours is marked expired.
  • Start over and Cancel drop every draft in the chat, so an older abandoned attempt cannot resurface as "an unfinished request".
  • Every answer is written to the draft as it arrives; a restart, a redeploy or a second worker continues the same booking.

8.5 Step 3 — the card and the yes

The card is built from the row, never composed by a model. Confirm re-checks the basics and the documents, then calls submit_booking_request(). The reply carries the booking reference; the PDF copy is queued in the outbox with its own idempotency key and delivered right after (section 10). The reference stays on the session so a second tap on the same card says "already with Operations" instead of apologising for a fault.

9. The document pipeline

 Telegram file update
   │  validate type/size (settings) → beginDocument(): row inserted, extracted.pending = true
   │  answer Telegram 200 immediately; the rest runs under waitUntil
   ├─ caption? → runFlow({kind:'caption'}) reads it onto the draft (patterns, then model)
   ├─ downloadFile → completeDocument():
   │     storeDocument (Storage) → readDocument (pdf.js text, or vision on a scan/photo)
   │     → extractDocument (type, chassis, numbers) → row updated, pending = false
   │     → attachToOpenBooking() by chassis when the row was not already attached
   ├─ media album? wait 1.5 s for siblings to record themselves
   ├─ any sibling still reading? → say nothing (the last to finish speaks for all)
   ├─ claimReply(chat, batch ids): unique row in notification_outbox — one speaker per batch
   └─ runFlow({kind:'document', batch})
         → "Received: …" + "Noted from your message: …" + the next question
  • Why answer Telegram first. Telegram delivers a chat's updates one at a time and waits for each answer before sending the next. Reading a file before answering made three files sent together read one after another, each getting its own reply. Recording the file and answering at once lets the three arrive within a second and be read in parallel.
  • One reply per batch. Readers that finish together all see "no sibling still reading", so the reply is claimed through the unique index on notification_outbox.idempotency_key; only the winner speaks, and the reply lists every file in the batch and every detail the caption supplied.
  • After a file the flow asks whatever is missing first — a basic, the MRN choice, more papers — and shows the card when nothing is. A client who sends an MRN is not asked whether they have one.
  • Papers for a request already with the desk (submitted, under review, waiting on the client, confirmed) are filed against it and acknowledged with its reference. Any inbound message from a client the desk is waiting on flips the request back to under review and raises a "client responded" task.
  • Wrong vehicle. A document whose chassis differs from the booking's is neither received nor missing: it is reported once per wrong chassis, before anything else.
  • Received is not verified. The bot may say received. Only Operations moves a document to verified, rejected or replacement requested.

10. Submission, notifications and the outbox

 something happens ──► notification_outbox row ──► drain ──► Telegram / email
 (one transaction)      (idempotency_key)           ├─ inline, right after the trigger
                                                    └─ /api/cron/outbox by hand or by cron
  • Retries at 1, 5, 15, 60, 240 and 720 minutes, then dead. A client who blocked the bot is marked dead at once. npm run outbox -- --list shows the queue; npm run outbox sends it.
  • On Confirm: the request PDF to the client (outbox), the Operations email with the PDF (Resend), the staff Telegram group ping, an Operations task, and optionally a Pumble message. None of these can affect whether the booking succeeded.
  • On the desk's decisions: booking_confirmed (+ confirmation PDF and shipment reference), booking_rejected with the reason, missing_information_requested, mrn_issued, free-form operations_message.
  • A pinned status card (one per chat, edited in place) follows open bookings and shipments and is removed when nothing is in flight.

11. Tracking

lib/flow/tracking.js extracts every candidate identifier from the message (bare, labelled, inside a sentence, an MKY-… reference) and matches each exactly against shipments (id, booking reference, ACID, B/L, container, vin_norm). A shipment is visible when the chat created it or the client behind the chat owns the booking; not-found and not-yours return the same answer. Ownerless seed rows are visible only with allow_unowned_shipment_tracking. Refresh re-queries by the reference carried in the button.

12. Talk to an agent, hours and tickets

  • supportHours() (lib/settings.js) reads support_hours_start/_end/_timezone and decides open or closed on an injectable clock, so the after-hours path is tested at fixed times.
  • In hours: a client_callback task is logged at once; the desk's details are shown; the client is asked what they need. A number on file (clients.phone, else the last booking) is used, not asked for.
  • After hours: the closing message and "Is it urgent?" (state CONTACT_URGENCY). Yes → the direct line if configured, else "flagged as urgent"; the ticket summary is prefixed URGENT: and the task is high priority; the closing message repeats the number. No → the question, and when the desk is back. A typed answer is understood, and marked urgent when it says "urgent" or "emergency".
  • A ticket needs a problem and a way to reach the client; they arrive in either order, and a client who declines to give a number is reachable through the chat. Tickets land in support_tickets and the console's Client Requests.

The console at /ops/ (and the earlier /ops.html) signs in with a name from ops_users and ADMIN_SECRET, sent as a header. 15. Security

  • The service-role key is server-only; RLS is on with no policies, so a leaked anon key reads nothing.
  • The webhook verifies Telegram's secret token; every update is claimed atomically; every callback payload is untrusted and checked against the real state.
  • Ownership rules on bookings and shipments; not-found and not-yours are indistinguishable.
  • The audit log redacts tokens, secrets, keys, file contents and anything over 500 characters.
  • The bot never reads out an unconfigured or placeholder phone number, and never invents a customs requirement.
  • docs/ROTATE-CREDENTIALS.md and npm run rotate cover rotating the bot token and keys.

17. Performance notes

  • The function runs in Frankfurt next to the database; from the default Washington region every database call crossed the Atlantic and a tap made eight of them.
  • Nothing that does not change the reply — the button acknowledgement, the typing indicator, the audit row, the pinned card — is waited for before the reply goes out. lib/background.js holds that work and the transport flushes it before returning, because a promise still in flight when a serverless function answers may never complete.
  • The client upsert and the "client responded" check run alongside the update claim; the draft sweep on the Book tap is gone; the assistant and the PDF libraries load only when needed.
  • Settings and the schema probe are cached per warm instance for a minute. The first request after a few idle minutes still pays Vercel's cold start.

18. Known limitations and open decisions

  • Decisions awaited from MKY: required_mrn_documents, acid_required, the real direct number, desk days off, SLA hours, whether free questions should go to an agent rather than the AI.
  • Hobby plan: cold starts; no cron more frequent than daily (queued messages go out on the next client message or desk action); twelve functions.
  • /api/chat is public and spends model credits; add a captcha, login or rate limiting before advertising it.
  • Two files that finish reading within the same few milliseconds race for the reply claim; the loser is silent, so at worst one reply — never two.
  • Migration 20260916120000_three_step_booking.sql seeds the hours and direct-number settings; the same rows were written to production directly and the migration is safe to apply later.
